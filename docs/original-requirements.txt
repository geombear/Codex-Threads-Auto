너는 시니어 풀스택 개발자이자 자동화 시스템 설계자다.

내가 운영하는 여러 Threads 계정에 일상글과 제휴마케팅글을 자동 생성하고, 계정당 하루 3회 예약 발행하는 프로그램을 만들어라.

설계나 화면 시안으로 끝내지 말고 실제 실행 가능한 프로그램, 검증 결과, 설치 방법, 운영 설명서까지 완성하라. 나는 비개발자이므로 관리자 화면과 사용 설명은 한국어로 작성하라.

아래 내용은 전체 요구사항이다. 요구사항을 임의로 생략하지 말되, 단계별로 구현하고 검증하라.

**1. 최종 목표와 기본 운영 방식**

프로그램은 다음 흐름을 지원해야 한다.

계정 연결 → 계정별 주제·말투 설정 → 상품·제휴 링크 등록 → 글감 선정 → 글 생성 → 검증 → 예약 → 본문 발행 → 자기 답글 발행 → 결과 확인 → 실패 복구 → 성과 확인

일상글과 제휴글을 명확히 구분한다.

일상글:
생활 속 공감, 관찰, 생각, 생활 정보, 운영자가 제공한 실제 경험을 바탕으로 작성한다.

제휴글:
자연스러운 상품 발견·공감형 본문과 사진·영상을 게시하고, 해당 게시물에 자기 답글로 경제적 이해관계 문구와 제휴 링크를 넣는다.

원하는 기본 게시 형태:

- 본문: 짧은 관심 유도 문장 + 공감 상황 + 검증된 제품 특징 + 필요한 사진·영상.
- 자기 답글: 경제적 이해관계 문구 + 간결한 상품 정보 또는 행동 안내 + 제휴 링크.
- 본문과 답글을 하나의 발행 묶음으로 관리한다.
- 필요하면 본문과 답글에 1/2, 2/2 같은 순번을 표시하는 옵션을 제공한다.
- 구매 링크는 기본적으로 자기 답글에 둔다.
- 광고 표시 문구의 위치와 형식은 아래 광고 표시 요구사항을 따른다.

짧고 자연스러운 말투를 구현하되, 실제로 하지 않은 구매·사용·전문가 추천을 사실처럼 만들어내지 않는다.

**2. 작업 진행 원칙**

먼저 현재 작업 폴더, 기존 프로젝트, 실행 환경, 관련 지침을 확인하라.

기존 프로젝트가 있으면 그 구조를 존중하고 활용하라. 없다면 유지보수하기 쉬운 구성을 선택해 구현하라.

작업을 막는 질문만 처음에 최대 5개로 묶어 질문하라. 답변이 없어도 진행 가능한 구현과 모의 테스트는 계속하라. 이미 합의된 내용을 반복해서 묻지 마라.

필수 외부 정보가 없으면 해당 연동만 미확인 상태로 남기고 나머지 작업을 완료하라. API 키가 없다는 이유로 관리자 화면, 데이터 구조, 예약, 모의 발행, 테스트까지 중단하지 마라.

다음 문서를 프로젝트 안에 유지하라.

- 전체 요구사항과 합리적인 기본값.
- 구조 및 주요 설계 결정.
- 단계별 작업 목록과 완료 상태.
- 확인한 공식 문서, 확인 날짜, 미확인 항목.
- 설치·운영·장애 복구 설명서.

긴 대화나 개발 도구 변경 후에도 이어서 작업할 수 있게 기록하라.

실제 게시, 유료 서비스 생성, 외부 공개 배포 등 운영에 영향을 주는 행동은 사용자가 승인한 범위에서 실행한다. 로컬 구현, 수정, 모의 테스트를 진행할 때마다 불필요하게 승인을 요구하지 마라.

**3. 공식 기능과 정책 확인**

개발 시점의 공식 자료를 확인하고 다음 사항을 문서화하라.

Threads:
- 본문 및 자기 게시물에 대한 답글 게시.
- 사진·영상·여러 미디어 게시 지원과 제한.
- OAuth 연결과 필요한 최소 권한.
- 토큰 교환·갱신·만료·권한 철회 처리.
- 개발 모드와 운영 모드의 차이.
- 계정 추가에 필요한 사용자 승인·앱 심사 조건.
- 글자 수, 미디어 규격, 호출 및 게시 제한.
- 게시 결과와 실제 게시물 ID·주소 확인 방법.
- 답글 대상 지정과 답글 작성 제한.
- 지원되는 통계 및 관련 권한.
- 링크 미리보기와 관련된 지원 범위.

제휴 프로그램:
- SNS 활동 채널 등록 조건.
- 상품 정보·이미지·영상의 사용 조건.
- 링크 발급·사용·변형·추적 관련 조건.
- 경제적 이해관계 표시 문구와 위치.
- 공식 상품 조회·링크 생성·실적 조회 API 제공 여부.

광고 표시:
- 공정위의 현행 경제적 이해관계 표시 기준.
- 매체와 표시 방식에 따른 적용 조건.
- AI 가상인물 등 추가 표시가 필요한 콘텐츠를 사용할 경우 해당 기준.

공식 자료에서 확인하지 못한 기능·권한·숫자를 추측하지 마라.
블로그나 강의의 경험칙을 공식 API 사양 또는 법적 허용 근거로 취급하지 마라.
사용 가능한 기능과 구현 제약을 먼저 확인하고, 지원하지 않는 기능은 가능한 것처럼 표시하지 마라.

Threads 공식 API를 우선 사용하라. 비공식 로그인, 계정 제한 회피, CAPTCHA 우회, 프록시 회전 등은 기본 구현에 포함하지 마라.

**4. 계정 관리와 확장**

운영자가 코드를 수정하지 않고 계정을 추가·연결·수정·중지·해제할 수 있게 하라.

계정 생성 자동화는 범위에 포함하지 않는다. 운영자가 소유하거나 관리 권한을 가진 계정을 연결한다.

계정별 설정:

- 운영 이름과 실제 Threads 식별자.
- 주제와 세부 카테고리.
- 대상 독자가 겪는 상황과 관심사.
- 말투, 존댓말·반말, 선호 표현, 금지 표현.
- 실제 사실과 경험 목록.
- 글쓰기 규칙 버전.
- 게시 시간대와 하루 예약 시간.
- 일상글·제휴글 비율.
- 사용 가능한 상품과 미디어.
- 제휴 프로그램과 광고 표시 설정.
- 글 생성 AI 공급자·모델.
- 비용 한도.
- 검토 후 발행 또는 자동 발행 모드.
- 초기 일상글 전용 기간.
- 계정별 운영 중지 상태.

말투를 위한 캐릭터 설정과 실제 인물의 이력은 분리하라. 계정 분위기를 만들기 위해 직업·가족관계·재산·경력·전문성을 꾸며내지 마라.

새 계정은 검토 후 발행 모드로 시작한다.
운영자가 자동 발행을 활성화하면 검증을 통과한 글은 매번 승인 없이 예약 발행한다.

계정별 토큰, 상품, 초안, 예약, 게시 기록, 비용을 분리하라.
다른 계정의 링크나 토큰으로 게시되는 문제가 없어야 한다.
계정 하나의 장애가 다른 계정의 작업을 막지 않게 하라.

**5. 하루 3회 발행과 예약**

하루 3회는 계정별 본문 게시물 3개를 의미한다.
본문에 딸린 자기 답글은 본문 발행 횟수와 별도로 집계하되 API 사용량에는 포함한다.

초기 기본값:

- 시간대: Asia/Seoul.
- 게시 시간: 08:00, 12:30, 21:30.
- 구성: 일상글 2개 + 제휴글 1개.
- 동일 계정의 동일 상품 재소개 간격: 14일.
- 사진·영상 없이 텍스트만 게시하는 일상글도 허용.
- 다음 날 사용할 글을 미리 생성하고 검증.

모두 운영 설정에서 변경할 수 있게 하라.
이 시간과 비율이 공식 최적값이라고 주장하지 마라.

일상글 3개당 제휴글 1개처럼 여러 날에 걸친 비율도 지원하라.
글 유형이 항상 같은 시간에만 배치되지 않도록 순환 옵션을 제공하라.
같은 날 제휴글 연속 배치 여부도 설정할 수 있게 하라.

예약 처리:

- 계정·운영 날짜·슬롯별 중복 예약 금지.
- 내부 시각은 UTC로 저장하고 운영 날짜는 계정 시간대로 계산.
- 서버 재시작 후에도 예약 유지.
- 게시 시간 변경 시 이미 실행된 작업과 대기 작업을 구분.
- 놓친 예약은 지연 허용 시간 안에서 처리하고, 초과하면 건너뛰거나 재예약.
- 미발행 글을 다음 실행 시 한꺼번에 몰아서 게시하지 않기.
- 실제 본문 게시 성공과 댓글 완료를 별도로 집계.
- 결과가 불확실한 발행을 실패로 간주하여 다른 본문을 추가 게시하지 않기.

제휴 상품이 부족하면 검증된 일상글로 대체하는 옵션을 제공하라.
검증된 콘텐츠가 없으면 해당 슬롯을 보류하고 이유를 표시하라.
하루 3개를 맞추기 위해 허위·중복·미검증 글을 발행하지 마라.

**6. 주제 보관함과 글감 수집**

계정별 주제 보관함을 만들고 약 20개 주제로 시작할 수 있게 하라.

주제별 저장 항목:

- 주제명, 카테고리, 대상 독자의 상황.
- 일상글·제휴글 활용 가능 여부.
- 연결 가능한 상품.
- 사용할 수 있는 사실·경험·출처.
- 우선순위, 사용 횟수, 최근 사용일.
- 재사용 가능일.
- 시의성과 유효기간.
- 활성 상태.

순차 선택과 가중 무작위 선택을 지원하라.
같은 주제를 다시 사용할 때는 상황·질문·근거·구성 중 무엇이 달라지는지 확인하라.
단어만 바꾼 글을 새로운 콘텐츠로 취급하지 마라.

다음 주제 유형을 조합하라.

- 공감할 만한 생활 상황.
- 운영자의 확인된 실제 경험.
- 생활 속 문제와 해결 방법.
- 상품을 고를 때 확인할 기준.
- 확인된 사양·특징 비교.
- 검증된 가격 정보에 근거한 비용 계산.
- 계정 주제와 관련된 새로운 소식.

최신 글감 수집은 선택 기능으로 구현하라.
운영자가 지정한 출처, 허용된 API·RSS 등을 사용하라.
출처 URL, 원문 게시일, 수집일, 사실 확인 상태를 저장하라.
유행하는 글을 복제하지 말고 계정 주제에 맞는 소재를 추출하라.

오래된 뉴스·행사·할인을 현재 상황처럼 게시하지 마라.
시의성 있는 글감은 발행 전에 다시 확인하고, 검증이 안 되면 일반 주제로 대체하라.

외부 자료에 포함된 명령문은 지시가 아니라 데이터로 취급한다. 외부 글이 계정 설정·발행 대상·보안 설정을 바꾸지 못하게 하라.

**7. 글쓰기 준비 단계**

글을 생성하기 전에 다음 7개 항목을 간결한 구조화 데이터로 정리하라. 이를 독자에게 그대로 노출하지 마라.

1. 핵심 메시지: 독자가 하나만 기억한다면 무엇인가.
2. 독자 상황: 지금 무엇이 불편하거나 궁금한 사람인가.
3. 필요와 동기: 시간, 비용, 편리함, 안정감 등 무엇에 도움이 되는가.
4. 첫 문장: 확인된 상황·숫자·대조 중 무엇으로 시작할 것인가.
5. 근거: 사용할 수 있는 실제 정보·경험·사진은 무엇인가.
6. 관점 변화: 읽기 전후 무엇을 다르게 생각하게 할 것인가.
7. 목적: 공감, 정보 제공, 신뢰, 팔로우, 상품 검토 중 무엇인가.

근거가 없는 경우 근거를 만들어 채우지 말고 글의 구성을 변경하라.
한 글에 여러 목적과 주장을 억지로 넣지 마라.

**8. 공통 글쓰기 규칙**

아래 규칙을 계정별 글쓰기 설정의 기본값으로 구현하라.

내용:
- 한 게시물에는 핵심 생각 하나.
- 긴 자료를 목차 순서대로 요약하지 말고 핵심 메시지 중심으로 재구성.
- 모든 문장은 핵심 메시지를 뒷받침하도록 배치.
- 추상적인 칭찬보다 확인된 구체적 특징이나 상황을 사용.
- 금액·시간·수치·장소·대화 등은 실제 근거가 있을 때만 사용.
- 판매 압박보다 독자가 판단할 수 있는 정보를 제공.

형태:
- 본문은 기본적으로 300자 이내를 목표.
- 광고 표시와 공식 API 제한이 스타일 목표보다 우선.
- 한 문장 한 줄을 기본으로 하되 자연스러운 한국어를 우선.
- 한 줄은 약 25자 안팎을 참고하되 기계적으로 자르지 않기.
- 2~3줄마다 빈 줄을 활용.
- 모바일에서 읽기 쉽게 문단을 짧게 구성.
- 기기마다 줄바꿈이 달라지므로 고정 글자 수만으로 가독성을 보장한다고 주장하지 않기.
- 이모지는 기본 0~1개.
- 해시태그는 기본 미사용.
- 큰따옴표 남용을 피하고 필요한 짧은 인용은 작은따옴표 사용.
- 인용문을 실제 발언처럼 만들어내지 않기.

말투:
- 친구에게 메시지를 보내듯 자연스러운 한국어.
- 문장 길이와 끝맺음을 적절히 변화.
- 짧은 감탄이나 혼잣말을 가끔 활용.
- ‘ㅋㅋ’, ‘ㅠㅠ’, ‘근데’, ‘아니 근데’, ‘그냥’ 등을 계정 성격에 맞게 제한적으로 사용.
- 존댓말·반말을 혼용하지 않기.
- 모든 문장을 같은 어미로 끝내지 않기.
- 특정 계정이나 유명인의 문장을 복제하지 않기.

기본적으로 피할 표현과 구성:
- ‘~인 사람?’, ‘~해본 적 있지?’로 매번 시작.
- ‘여러분’, ‘결론부터 말하면’, ‘핵심은’, ‘정리하자면’.
- ‘첫째, 둘째, 셋째’ 식의 발표문 같은 나열.
- 본문을 번호·불릿 목록으로 채우기.
- 억지 반전, 과도한 감탄, 근거 없는 숫자.
- 명언·교훈·거창한 결론으로 매번 마무리.
- 근거 없는 ‘무조건’, ‘역대급’, ‘최저가’, ‘품절 임박’.
- 모든 글에 댓글·팔로우·구매 요청 붙이기.

이 규칙은 자연스러움을 위한 기본값이다. 광고 고지, 사실 정확성, 가독성을 해치면서까지 기계적으로 적용하지 마라.

**9. 일상글과 제휴글의 구체적인 구성**

일상글의 기본 구성:
관찰 또는 공감 상황 → 생각이나 유용한 정보 하나 → 짧은 여운

일상글에는 제휴 링크를 억지로 연결하지 마라.
운영자가 실제 경험을 제공하지 않았다면 ‘어제 내가’, ‘우리 아이가’, ‘직접 해봤는데’ 같은 개인 경험을 만들지 마라.
일반적인 상황·관찰·정보형 문장으로 작성하라.

제휴글의 기본 구성:
공감 상황 또는 상품 발견 → 확인된 제품 특징 하나 → 적합한 사용 상황 → 필요한 경우 답글 안내

예를 들어 실제 경험 자료 없이 ‘카페에서 보고 바로 결제했다’고 쓰지 말고, ‘카페에서 자료랑 작업창을 번갈아 보는 상황’처럼 일반적인 불편에서 시작하라.

제휴글은 다음 네 관점으로 순환한다.

- 경험담: 확인된 실제 사용 자료가 있을 때만 사용.
- 문제 해결: 상품의 검증된 기능과 생활 상황을 연결.
- 비교 후 선택: 출처가 있는 비교 기준으로 설명. 직접 써본 것처럼 표현하지 않기.
- 가격과 절약: 확인된 가격과 명시된 가정으로 계산.

가격 비교나 하루 비용 계산은 계산 근거를 저장하라.
개인적인 만족을 객관적인 성능이나 누구에게나 보장되는 효과로 바꾸지 마라.

본문의 제품명은 자연스럽게 필요한 만큼 사용한다. 제품명을 줄인다고 광고 여부가 사라진다고 가정하지 마라.

**10. 실제 사실·경험·상품 근거 관리**

계정의 문체 설정과 사실 정보를 별도로 저장하라.

계정 사실 목록:
운영자가 확인한 직업, 경력, 성과, 실제 경험, 표현 가능한 개인 정보.

경험 목록:
언제, 누가, 무엇을 경험했는지, 어떤 표현까지 가능한지, 근거와 사용 허용 범위.

상품별 항목:
- 제휴 프로그램과 상품 식별자.
- 상품명, 카테고리, 옵션.
- 원본 상품 URL과 실제 제휴 URL.
- 적용 계정 또는 공유 허용 범위.
- 확인된 특징·장점·한계.
- 적합한 사용 상황.
- 실제 사용 자료 유무.
- 가격·배송·재고 등 변동 정보와 확인 시각.
- 광고 표시 문구.
- 사용 가능한 미디어와 권리 정보.
- 최근 게시일과 재사용 가능일.
- 활성 상태.

주장의 근거와 사용 가능 기간을 추적하라.

다음 내용은 근거 없이 생성하지 마라.

- 직접 구매·사용·결제했다는 표현.
- 가족·친구·고객이 보였다는 반응.
- 의사·전문가·유명인의 추천.
- 일정 거리·기간 사용 후 효과.
- 건강·치료·통증 개선 효과.
- 원산지·성분·인증·시험 결과.
- 구체적인 매출·수입·절약 금액.
- 최저가·할인율·재고·배송 도착일.

원산지나 성분표 사진에서 일부 항목만 확인된 경우 전체 원료에 대한 주장으로 확대하지 마라.

건강·효능 등 별도 검토가 필요한 주장은 자동 발행에서 보류할 수 있도록 분류하라.

**11. 제휴 링크와 미디어**

초기 버전은 운영자가 발급한 제휴 링크를 직접 등록하는 방식으로 완전히 동작해야 한다.
공식 API 사용 권한이 있으면 상품 조회·링크 생성 기능을 추가하라.

AI가 링크나 추적 파라미터를 만들어내지 못하게 하라.
등록된 정확한 URL을 프로그램이 삽입하라.
링크 단축·변형·추적 기능은 제휴사의 허용 범위를 확인한 경우에만 사용하라.

여러 링크를 넣는 경우:
- 서로 다른 상품·옵션이면 구분 설명 제공.
- 같은 링크의 기계적 반복은 기본값에서 제외.
- 링크별 상품과 본문 설명의 일치 검증.
- 링크 미리보기는 플랫폼이 결정하는 부분을 구분.
- 카드 이미지·제목·노출 순서를 완전히 통제할 수 있다고 보장하지 않기.

링크 점검으로 인위적인 제휴 클릭이나 통계 왜곡이 발생하지 않게 하라.
가능한 범위에서 URL 형식·허용 도메인·목적지를 확인하라.
외부 URL을 읽을 때 내부망 접근, 위험한 리다이렉트, 과도한 응답 크기를 차단하라.

미디어 관리:
- 사진·영상의 원본, 출처, 사용 권한, 연결 상품 저장.
- 실제 촬영물, 판매자 제공물, AI 생성물을 구분.
- 타인의 게시물에서 이미지를 무단 복제하지 않기.
- AI 이미지나 판매자 사진을 운영자의 실사용 증거로 취급하지 않기.
- 본문과 사진의 상품·옵션 일치 확인.
- 공식 규격에 따른 크기·용량·형식 검사.
- 필요한 대체 텍스트 작성.
- 업로드·변환·처리 실패와 만료된 미디어 주소 처리.
- 미디어 처리 완료를 확인한 뒤 게시.
- 미디어를 빼면 본문 의미가 달라지는 경우 텍스트만 임의로 발행하지 않기.

**12. 광고 표시와 자기 답글**

광고 고지와 링크는 AI의 자유 생성 영역에서 분리하고, 검증된 설정값을 프로그램이 삽입하라.

순수 일상글에는 광고 문구를 일괄 적용하지 마라.
제휴 상품 소개와 구매 유도가 있는 본문은 링크가 자기 답글에 있더라도 제휴 콘텐츠로 분류하라.

본문의 짧은 광고 표시와 자기 답글의 상세 경제적 이해관계 문구를 별도 설정으로 관리하라.

- 본문 첫 부분에는 ‘[광고]’ 등 짧고 명확한 표시를 사용하는 방안을 지원.
- 실제 적용 문구와 위치는 현행 공적 기준과 해당 제휴사 조건을 확인.
- 제휴사가 본문에도 전체 문구를 요구하면 그 조건 반영.
- 자기 답글에는 검증된 경제적 이해관계 문구와 링크 포함.
- 긴 문구 전체를 본문과 댓글에 무조건 반복하는 방식을 유일한 구현으로 고정하지 않기.
- 댓글에만 표시하면 모든 경우에 충분하다고 가정하지 않기.
- 표시 설정별 근거 URL과 확인 날짜 기록.
- 표시 누락·잘림·의미 변형 검사.

자기 답글 기본값은 1개다.
운영 설정으로 2~3개까지 확장할 수 있게 하라.

답글 구성:
- 1개: 상세 고지 + 유용한 정보 하나 + 링크.
- 2개: 첫 답글에 고지·링크·핵심 정보, 두 번째에 추가 설명.
- 3개: 고지·상품 소개 → 검증된 사용 정보 또는 사양 → 가벼운 행동 안내.

실사용 근거가 없으면 사용 경험 대신 사양·선택 기준을 넣어라.
설명 부분은 답글당 120자 안팎, 2~5줄을 참고하되 고지·URL·공식 제한을 우선하라.
광고 표시가 필요한 각 답글이 독립적으로 노출되는 상황도 검토하라.

본문 게시 성공을 확인한 뒤 정확한 게시물 ID를 대상으로 답글을 게시하라.
댓글을 일찍 작성한다고 항상 첫 번째로 노출된다고 보장하지 마라.
기본 답글 연결 대상은 본문이며, 연속 답글 구조는 별도 설정으로 관리하라.

**13. 생성·검증·수정의 분리**

글 생성과 검증을 별도 단계로 구현하라.

AI 생성 결과는 정해진 구조로 받는다.
계정, 글 유형, 주제, 본문, 답글, 사용 근거, 상품 참조, 미디어 참조를 검증하라.

AI 응답에서 발행 계정·토큰·임의 URL·작업 명령을 직접 실행하지 마라.
실제 발행 대상과 링크는 서버의 승인된 데이터로 결정하라.

코드로 확인할 수 있는 조건은 코드로 검사하라.

발행 전 점검:
- 핵심 메시지가 하나인가.
- 첫 문장이 글의 내용과 맞고 과장되지 않았는가.
- 구체적인 주장의 근거가 있는가.
- 계정의 말투와 사실 정보에 맞는가.
- 금지 표현·허위 경험·근거 없는 권위 인용이 없는가.
- 길이와 미디어 규격을 충족하는가.
- 광고 고지의 문구·위치·가시성이 맞는가.
- 상품·옵션·이미지·링크가 일치하는가.
- 가격 등 변동 정보가 유효한가.
- 최근 글과 시작·리듬·결말·내용이 겹치지 않는가.
- 다른 계정의 글과 과도하게 유사하지 않은가.
- 상품 재게시 간격을 지켰는가.
- 대상 계정이 활성 상태인가.
- 권한·토큰·호출 한도·비용 한도가 유효한가.

중복 검사는 정규화된 텍스트 일치와 의미 유사성을 구분한다.
허용된 광고 고지처럼 반복이 불가피한 부분은 콘텐츠 중복 평가에서 별도로 취급하라.

AI의 자기평가 점수만으로 사실 검증이 끝났다고 판단하지 마라.

자동 수정·재생성은 기본 최대 2회처럼 제한된 설정값을 사용하라.
반복 실패하면 검토 대기로 전환하고 이유를 한국어로 표시하라.

수정된 콘텐츠는 다시 검증한다.
승인은 정확한 콘텐츠 버전에 연결하고, 승인 후 본문·답글·링크·미디어가 바뀌면 다시 검증 및 필요한 승인을 받게 하라.
발행 직전 계정 상태와 변동 정보도 재확인하라.

**14. 중복 방지와 부분 실패 복구**

핵심 품질 기준은 중복 없이 게시하고, 실패한 단계부터 복구하는 것이다.

발행 묶음, 본문, 개별 답글의 상태를 따로 저장하라.

최소 상태:
초안 / 생성 중 / 검증 실패 / 검토 대기 / 예약 완료 / 발행 중 / 본문 게시 완료 / 답글 일부 실패 / 전체 완료 / 결과 확인 필요 / 보류 / 취소

필수 설계:
- 계정·운영 날짜·슬롯에 대한 데이터베이스 중복 방지 제약.
- 작업자 간 동시 실행 방지와 만료 가능한 잠금.
- 작업자 중단 후 안전한 작업 회수.
- 본문과 답글별 내부 중복 방지 식별자.
- 데이터베이스 기록과 작업 큐 전달 사이의 작업 유실 방지.
- API 컨테이너 ID와 실제 게시물 ID의 명확한 구분.
- 각 시도 시각, 응답, 오류 분류, 게시물 ID 기록.
- 게시 완료 결과의 가능한 범위 내 재확인.

본문 성공 후 답글이 실패하면 본문을 다시 게시하지 마라.
여러 답글 중 일부가 성공하면 성공한 답글은 재전송하지 마라.

게시 요청 후 응답이 끊겼다면 실패로 단정하지 마라.
공식 API로 실제 게시 여부를 확인하고, 확정이 안 되면 ‘결과 확인 필요’로 보류하라.
내부 중복 방지 키만으로 외부 API의 완전한 단일 게시를 보장한다고 주장하지 마라.

오류 처리:
- 일시 오류·호출 제한: 제한된 재시도와 점진적 대기.
- 인증·권한 오류: 해당 계정만 중지하고 재연결 안내.
- 콘텐츠 오류: 검토 대기 또는 제한된 수정.
- 결과 불확실: 확인 전 재전송 금지.
- 무한 재시도 금지.
- 원인을 고치지 않은 수동 재시도 반복 방지.

본문 삭제나 전체 재게시를 기본 복구 방식으로 사용하지 마라.
본문은 성공했지만 답글이 미완료인 상태를 운영 화면에서 명확히 표시하라.

**15. 한국어 관리자 화면**

비개발자가 코드 수정 없이 운영할 수 있어야 한다.

대시보드:
오늘 예정·완료·실패·보류 건수, 본문 성공과 답글 완료 구분, 연결 상태, 토큰 만료, 초안 부족, 비용, 조치가 필요한 문제.

계정 관리:
연결, 추가, 말투·주제·시간·비율 변경, 시험 운영, 자동 발행 전환, 중지, 해제.

콘텐츠 검토:
본문과 답글을 한 묶음으로 미리보기, 사진·영상 확인, 근거 보기, 수정, 재생성, 승인, 보류, 취소.

예약 달력:
계정별·날짜별·유형별 예약 조회와 변경.

상품·링크·미디어 관리:
등록, 수정, 사용 권한, 검증 상태, 정보 확인일, 연결 계정, 재게시 간격.

주제 관리:
주제 목록, 사용 기록, 새 글감 제안, 순환 순서.

발행 기록:
실제 게시물 주소, 계정, 시각, 본문·답글별 결과, 오류, 재시도, 운영 변경 기록.

규칙 관리:
글쓰기 규칙 버전, 변경 전후 비교, 복원, 운영자 수정에서 추출한 개선 제안.

설정:
AI 공급자·모델, 비용, 검증 기준, 광고 표시, 알림 수신처.

전체 긴급 중지:
새로운 외부 게시 요청을 차단한다.
이미 전송된 요청까지 취소된다고 표시하지 말고 결과를 확인한다.
재개할 때 밀린 글을 한꺼번에 게시하지 않는다.
계정 중지·연결 해제도 실제 외부 요청 직전에 확인한다.

화면에는 상태와 다음 행동을 쉬운 한국어로 표시하라.
모바일에서도 초안 확인과 중지가 가능하게 하라.
지원하지 않는 기능을 동작하는 버튼처럼 만들어 놓지 마라.

**16. 시험 운영·규칙 개선·성과**

새 계정은 실제 게시 없이 3일치 본문 9개와 필요한 답글을 생성하여 검토할 수 있게 하라.
말투, 사실, 중복, 상품 연결, 고지를 평가하라.
날짜가 지났다는 이유로 자동 발행을 켜지 마라.

초기 일상글 전용 기간은 시험 운영과 별도로 관리한다.
0일·7일·14일 등으로 설정할 수 있게 하되, 플랫폼의 공식 필수 조건이나 계정 안전 보장으로 설명하지 마라.

운영자의 수정 전후를 저장해 계정별 글쓰기 개선안을 제안하라.
한 번 수정한 내용을 모든 계정에 자동 적용하지 마라.
규칙 변경은 운영자가 채택한 뒤 적용하고 대표 초안으로 비교할 수 있게 하라.

통계:
- 공식 API나 제휴사에서 실제 제공하는 항목만 수집.
- 조회·반응·클릭·주문·매출·수익 구분.
- 수집 불가 값은 0 대신 ‘수집 불가’.
- 수익은 확보된 자료에서 잠정·확정·취소를 구분.
- 허용된 식별 방법이 있을 때만 게시물과 제휴 성과 연결.
- 게시 후 같은 경과 시간을 기준으로 비교.
- 표본이 적으면 결론 보류.
- 관측된 차이를 알고리즘 인과관계로 단정하지 않기.

주제·문체·게시 시간의 개선안을 제안하되, 반응이 좋다는 이유로 게시량이나 광고 비중을 자동 증가시키지 마라.

**17. 기술 구조·보안·비용·운영**

소규모로 시작하되 계정이 늘어도 핵심 구조를 다시 만들지 않게 설계하라.

기존 프로젝트가 없다면 TypeScript 기반 웹 화면·백엔드와 PostgreSQL을 우선 검토하라.
작업 큐는 영속성·동시 실행 제어·재시도를 만족하는 단순한 구성을 선택하라.
초기부터 불필요한 마이크로서비스나 복잡한 운영 도구를 늘리지 마라.

다음 역할을 분리하라.

- 관리자 화면과 관리자 인증.
- 계정 연결 및 토큰 관리.
- 콘텐츠·주제·상품·미디어 관리.
- 생성과 검증.
- 예약 관리.
- 본문·답글 발행 작업자.
- 게시 결과 확인과 복구.
- 통계와 비용.
- 감사 기록과 알림.

예약 상태를 브라우저나 메모리에만 저장하지 마라.
화면을 닫아도 백엔드가 계속 실행되도록 하라.
로컬 컴퓨터가 절전·종료되면 실행되지 않는다는 점을 설명하고, 상시 서버 운영 경로를 제공하라.
Windows 환경에서 따라 할 수 있는 설치 방법도 제공하라.

보안:
- 관리자 인증과 서버 측 접근 제어.
- OAuth 요청 검증과 세션 보호.
- 최소 권한 요청.
- 토큰 암호화 저장과 암호화 키 분리.
- 비밀값을 소스·브라우저·로그·AI 입력에 노출하지 않기.
- 오류 로그에서 민감정보 제거.
- 계정 연결 해제 시 대기 작업 차단.
- 파일 업로드의 형식·크기 검사.
- 외부 URL 접근 제한.
- 운영 변경과 게시 시도 감사 기록.
- 백업과 실제 복원 절차.
- 사용자 승인 없이 외부에 공개하거나 유료 인프라를 생성하지 않기.

AI:
- 공급자와 모델을 교체할 수 있게 분리.
- 생성 결과 구조 검증.
- 계정별·전체 사용량과 비용 기록.
- 무한 재생성과 호출 금지.
- 동시 호출에서도 비용 한도가 과도하게 초과되지 않도록 예약·정산.
- 비용 한도 초과 시 새 생성은 중단하고, 이미 검증된 예약글 처리 정책은 별도로 적용.

개발 도구 구독료, 운영 중 AI 호출 비용, 서버·저장소 비용을 구분하라.
개발 도구를 구독했다는 이유로 운영 중 모든 생성 비용이 포함된다고 가정하지 마라.

계정 N개일 때 기본 본문 수는 하루 3N개다.
댓글, 미디어 처리, 재생성, 검증, 결과 조회 비용도 계산하라.
단가에는 출처와 확인 날짜를 남기고 계정 수별 예상 사용량을 보여줘라.

토큰 만료, 검증된 초안 부족, 상품 부족, 댓글 미완료, 작업자 중단을 감지하라.
알림은 운영자가 설정한 수신처로만 보내고, 같은 문제의 반복 알림을 제한하라.

**18. 구현 순서와 테스트**

다음 단계로 구현하라. 각 단계에서 동작을 확인하고 작업 문서에 기록하라.

1단계:
환경 조사, 공식 기능 확인, 요구사항·기본값·외부 의존성 정리.

2단계:
데이터 구조, 관리자 인증, 계정 설정, 상품·주제 관리, 영속 예약.
모의 시각과 모의 Threads API로 동작 검증.

3단계:
콘텐츠 생성, 사실 근거 연결, 광고 문구 삽입, 검증, 미리보기, 승인.

4단계:
실제 Threads 연결, 미디어 처리, 본문과 자기 답글 발행, 결과 확인.

5단계:
중복 방지, 응답 유실, 부분 실패 복구, 비용 제한, 알림, 긴급 중지.

6단계:
규칙 개선, 통계, 확장 검증, 설치·운영 문서, 최종 점검.

필수 테스트:

- 계정마다 다른 말투·시간·상품·링크 사용.
- 계정 사이의 데이터·토큰 혼선 방지.
- 코드 수정 없는 계정 추가.
- 계정당 하루 본문 3개와 답글 별도 집계.
- 여러 날에 걸친 일상글·제휴글 비율.
- 시간대 날짜 경계와 예약 시간 변경.
- 재시작·중복 작업 전달·동시 작업자의 중복 방지.
- 작업자 종료 후 안전한 재개.
- 본문 성공 후 답글 실패 시 답글만 복구.
- 답글 일부 성공 시 성공한 답글 재전송 방지.
- 게시 성공 직후 응답 유실 시 결과 확인.
- 미디어 처리 실패와 만료된 주소.
- 광고 문구 누락·잘림·변형 차단.
- 다른 상품·옵션·계정의 링크 혼입 차단.
- 근거 없는 경험·추천·가격·효능 표현 보류.
- 오래된 뉴스·할인·상품 정보 처리.
- 승인 후 변경된 콘텐츠 재검증.
- 토큰 만료·권한 철회·호출 제한 처리.
- 자동 발행 계정의 정상적인 무인 처리.
- 계정 중지·전체 중지·연결 해제 이후 신규 발행 차단.
- 비용 한도와 재생성 한도.
- 모의 환경에서 계정 1개·10개·50개·100개 처리.
- 백업에서 예약·게시 기록 복원.

실제 대량 게시로 부하 테스트하지 마라.
정상 응답만 반환하는 모의 API로 테스트를 끝내지 말고 지연·실패·응답 유실을 재현하라.

실제 계정 테스트는 사용자가 지정한 계정과 확인한 콘텐츠로 진행하라.
필수 권한·인증이 없으면 모의 검증 완료와 실제 연동 미확인을 구분하라.
비밀값을 채팅에 붙여 넣게 하지 말고 안전한 입력 화면이나 환경 설정 방법을 안내하라.

**19. 최종 산출물과 완료 기준**

최종 산출물:

- 실행 가능한 프로그램.
- 데이터베이스 마이그레이션.
- 비밀값이 없는 환경 설정 예시.
- 모의 실행용 계정·상품·글감 데이터.
- 자동 테스트와 실제 실행 결과.
- 한국어 설치·실행 설명서.
- 계정 연결·추가·중지·재연결 방법.
- 상품·링크·미디어 등록 방법.
- 시험 운영에서 자동 발행으로 전환하는 방법.
- 로컬 실행과 상시 서버 운영 방법.
- 장애 복구·백업·복원 방법.
- 공식 자료 출처와 확인 날짜.
- 계정 수별 예상 사용량·비용.
- 구현 완료와 미완료 항목.

최종 보고는 다음을 명확히 구분하라.

- 구현 완료.
- 모의 테스트 통과.
- 실제 외부 연동 확인.
- 사용자 설정이 필요한 항목.
- 외부 권한·심사 때문에 미확인인 항목.
- 알려진 한계.

화면만 있는 데모, 가짜 성공 응답, 동작하지 않는 버튼을 완성품으로 제시하지 마라.
지원되지 않는 API 기능을 있다고 주장하지 마라.
오류가 없거나 계정 제한이 절대 발생하지 않는다고 보장하지 마라.

정상적인 경우에는 자동으로 동작하고, 불확실한 경우에는 중복·허위 게시를 피하면서 운영자가 원인과 다음 행동을 알 수 있어야 한다.

이제 현재 환경부터 확인하고, 전체 요구사항을 작업 문서로 정리한 다음 단계별 구현을 시작하라.
